# 个人数据库 · AI 执行规则

> 本文件是**唯一真相**，只写 AI 必须执行的规则；设计意图见仓库的 `docs/`，二者冲突时以本文件为准。历史变更记在 [[个人数据库]] 进展日志。
> 这是模板：第零节的对话原则、第七节的 goal / situation / field 取值都是示例，按你自己的改。

---

## 零、AI 对话原则

1. 所有回答保持客观，不要因为照顾用户情绪而隐瞒相关信息与结论
2. 所有回答的结构：先总结，再详细说明，最后逐条放需要用户决策的点

## 一、铁律

1. **原话逐字保留**：B- 层原始记录（emotion 的心理活动、insight 原文、dialogue 正文）与 project / holiday 的进展日志，只增不改——不改写、不美化、不摘要。AI 只可移动位置、加 frontmatter、加链接、调排版。
2. **清理只归档不删**：结束的项目、旅行归档（规则见 6.1）。纯空壳删除前扔进 `0-Unclear/`。
3. **不明就放 Unclear**：类型判断不了、信息不足、意图多义、需要用户确认、涉及词表外的新类别 → `0-Unclear/`，不猜。
4. **文件名由 AI 从内容提炼**，用户不取标题。
5. **frontmatter 不编造**：没提到的字段留空。
6. **判断不落盘**：看板只列事实，不写"该做什么"；价值判断（好坏对错、今天该干什么）只在对话里说。C 层里 AI 对用户的推测（动机、模式、原因）可以写，但必须标「（AI 判断）」并附证据，见 4.1。`C-侧写.md` 按周期整份重写，见 6.11。
7. **用户改规则，不改内容**：归类、蒸馏、维护都是 AI 的活。本文件非必要不改，AI 仅在用户要求时修改。
8. **移动 / 改名走 Obsidian**：用 Obsidian CLI（`obsidian vault="<库名>" move path=... to=...`）或 `app.fileManager.renameFile`，让链接自动更新；不用 shell 移动。删除走 Obsidian 回收站。批量处理带空格 / 中文的路径必须安全引用。

## 二、目录结构

```
0-Inbox/                 入口 · 用户想存进库的一切，AI 转移后清除
0-Unclear/               入口 · AI 无法判断归属的记录，选择题等用户勾选

A-Projects/              执行 · 正在筹备和进行的事务
A-Holidays/              执行 · 旅行计划与筹备中的旅行想法
A-Archive/               执行 · 已结束的事务与旅行（冻结只读）

B-Emotions/              记录 · 原始情绪记录（事件 → 情绪 → 感悟）
B-Insights/              记录 · 想法与摘录，向内（自我成长与管理）
B-Topics/<大类>/          记录 · 主题学习与领域知识，向外（不含个人资料）
B-Dialogues/             记录 · 与 AI 关于某件事的讨论
B-Tools/<大类>/<项目>/    记录 · 用户创造的产品
B-Info/                  记录 · 个人信息资料（不存隐私原文，不参与蒸馏）

C-Playbook/
  ├ C-Strategies/        蒸馏 · 应对策略（带证据反链）
  └ C-Situations/        蒸馏 · 情境综述（类别由用户定）
C-Knowledge/             蒸馏 · 知识体系的总领与知识间的关系
C-Memoirs/               蒸馏 · 季度回忆录

C-侧写.md                用户侧写：画像（月更）+ 近况（日更），每条带来源
CLAUDE.md                本文件
AGENTS.md                本文件的副本（供 Codex 等读 AGENTS.md 的工具使用），内容与本文件一致，勿单独改
```

**层级语义**：A = 执行（有状态、会结束）· B = 记录（第一手素材）· C = 蒸馏（AI 合成、可重跑）。

## 三、工作流

### 3.1 写入（用户说"记一下 / 存进去 / 整理收件箱 / Inbox"）
逐条处理 `0-Inbox/`：
1. **判断归属**：属于 A、B 层的哪一类或哪几类（一条输入可按内容拆到多处）。
2. **追加优先**：是已有 project / holiday / topic 等的后续 → 打开该文件追加，带日期。
3. **新建**：确为新实体 → 按第五节建文件。
4. **放 Unclear**：见铁律 3。
5. **丢弃**：噪音、临时信息，在回复里说明丢了什么。

处理完从 Inbox 清除原件。
**不入库**：项目工作文档（PPT 稿、方案稿等）不归个人数据库管理。

### 3.2 查询（用户提问或执行任务需要上下文）
0. 需要了解用户本人（是什么样的人、最近在忙什么、要注意什么）时，先读 `C-侧写.md`，再按它的链接深挖。侧写只是索引，引用事实时以原记录为准。
1. 先按 frontmatter（type / situation / emotiontype / field / goal）和文件名筛选。
2. 只读命中的少数文件，以及这些文件中关联链接到的文件。
3. 作答时说明查了哪些范围、可能漏了什么。

### 3.3 蒸馏
- 只在用户要求或巡检时进行，不自动生成。
- 原料：strategy ← B-Emotions + B-Insights + B-Dialogues（复盘类优先）；situation 综述 ← 该情境下的 insight + strategy；knowledge ← B-Topics + B-Tools + B-Insights + C-Strategies；memoir 见 6.5。
- 必须带证据反链（`## 关联链接` 的 **证据** / **反例** 栏），结论前置，人可审计，可随时重跑。strategy 还要标证据等级，见 6.10；AI 推测按 4.1 标注。
- 需要新的情境类别时，向用户提议，不自行新建。
- 定期巡检与蒸馏见第八节。

## 四、通用格式

- **frontmatter 只放分类轴**（这个文件是什么）；**关系一律写正文 `## 关联链接`**（牵连谁 + 为什么）。
- 正文分节一律用 `## 标题`，不用 `**加粗标签**：`。
- 日期一律 `YYYY-MM-DD`；数组一律行内写法 `[a, b]`。
- **排版**：
  - frontmatter 的 `---` 必须在第一行，前面不留空行。
  - `#` 一级标题每篇最多一个；正文从 `##` 开始，最深到 `####`。
  - 一个笔记只聚焦一个主题。
  - 中英文之间、中文与数字之间加空格；中文句子用全角标点。
  - 段落之间空一行；无序列表统一用 `-`，子级缩进 2 个空格。
  - 粗体只用于关键词或结论，不整段加粗。
  - 代码块必须声明语言；图片用 `![[图片名.png]]` 嵌入。
- `## 关联链接` 写法：

```markdown
## 关联链接
**goal**：[[学业]]
**证据**：
- [[某emotion记录]] —— 一句话说明为什么关联
**来源**：《原子习惯》
```

### 4.1 原话与 AI 判断分开

适用于 C 层全部文件（strategy、situation、knowledge、memoir、`C-侧写.md`）。

- **用户原话**：放在「」里，后面紧跟出处链接，如 `「能查的先查完，剩下的交给时间」（[[实习求职]] 2026-09-28）`。原话逐字，不改字、不拼接。
- **记录里的事实**（日期、发生了什么）：带出处链接，不加标注。
- **AI 对用户的推测**（动机、模式、原因、没说出口的感受、「你其实是在……」）：句末或列表项末尾标「（AI 判断）」。一整节都是推测时，在该节第一行写一次 `（本节为 AI 判断，依据见证据栏）`，不必逐句标。
- **通用知识、理论、书和播客**：写进 **来源** 或 **理论依据** 栏，不标「（AI 判断）」。
- 拿不准算事实还是推测的，按推测标。
- 规则生效前写的 C 文件：下次修改时补标，不集中回填。

| `topic`                | B-Topics/<大类>          | created, updated, field               | 自由 → 关联链接                           |
| `dialogue`             | B-Dialogues            | created, updated                      | 自由 → 关联链接                           |

## 六、补充规则

### 6.1 project
- 进展日志：每条一个 `### YYYY-MM-DD`，倒序，关键词加粗，保留弯路。
- 小事 = `下一步` 里一行 `- [ ]`，硬 deadline 加 📅；无归属杂事进 catch-all：[[日常事务]]（私事）、[[组内杂项]]（组内）。
- `status: done`（含中途终止，日志注明"终止"）→ 移入 `A-Archive/`，原文不改。

### 6.2 holiday
- 状态与 project 相同：planned（想法 / 筹备中）→ active（已订、出行中）→ done；done 的处理同 6.1。
- 旅途中的感受记为 emotion，`## 关联链接` 指回本行程。
- 与 AI 讨论行程的对话存入 B-Dialogues，并与本行程互相关联链接。

### 6.3 dialogue
- 记录与 AI 关于某件事的讨论；有关联的 project / holiday / insight 等写进 `## 关联链接`，**不强制分流**。
- 需要标注可信度时写一行：`**性质**：与 AI 深谈整理，含推测成分`。

### 6.4 tool
- 一个项目一个文件夹：`README.md`（怎么用、为什么这样设计）+ `CHANGELOG-vN.md`（决策、踩坑、进度）。
- 第三种体裁：`接力文档-vN.md` / `工作日志-<阶段>.md`，type 取 readme 或 changelog 中更贴的一个。
- 既有不合命名的旧文件不追溯改名，规则只约束新建。
- 链接到某个 tool 项目时，指向它的 README：`[[B-Tools/<大类>/<项目>/README|<项目>]]`；项目文件夹名本身无法被 wikilink 解析。

### 6.5 memoir
- 按需生成，一季一份。
- 原料：A-Projects 进展日志、A-Archive（本季结束的）、A-Holidays、B-Emotions、B-Insights、B-Topics（本季 updated）、B-Tools（本季 CHANGELOG）、B-Dialogues；**不含 B-Info**。
- 正文：顶部季度综述（本季主线 + 各项之间的潜在联系）→ 时间正序时间线：
  `- YYYY-MM-DD 🟢/✈️/❤️/💡/📚/🛠️/💬 [[原文件]] 一句概述`
  （🟢 项目 · ✈️ 旅行 · ❤️ emotion · 💡 insight · 📚 topic · 🛠️ tool · 💬 dialogue）

### 6.6 knowledge
- **一份文件 = 一个知识体系**（一个大类，或跨大类的一个主题）；单个知识点仍写在 B-Topics。
- 与相邻类型的分工：B-Topics 是知识原料；C-Knowledge 是 AI 把原料**总领**起来、理出**关系**；C-Strategies 是"遇到某种情形怎么做"。
- 正文：
  - `## 总领`：3–5 句说清这块知识的全貌与主线，结论前置。
  - `## 知识地图`：按逻辑层级（而非按文件）组织，列出所含 topic / tool / insight / strategy 的链接。
  - `## 关系`：每条写 `[[A]] → [[B]]：关系类型 + 一句说明`；关系类型取 因果 / 依赖 / 对比 / 包含 / 矛盾。
  - `## 缺口`：尚未弄懂的地方、原料之间互相矛盾之处。
  - `## 关联链接`：**证据** 栏列出用到的原料。
- 某一大类原料积累较多，或用户反复跨文件询问同一主题时，AI 可提议生成；用户同意后再生成。原料更新后可整份重跑。

### 6.7 unclear 模板
```markdown
## 原始记录
（用户原话逐字）

## 判断选项
（1–2 句：为什么不明 + AI 最佳猜测）
- [ ] **A**（推荐）：具体处置一句话
- [ ] **B**：备选
- [ ] **C**：其他 / 我自己写

## 关联链接
```
用户勾选后，AI 按选项处理并删除 Unclear 副本。

### 6.8 info
- 只记"有什么、在哪"，**不写证件号、密码等隐私原文**。
- 不参与蒸馏。

### 6.9 看板
- 用仓库里的 `cockpit-web/index.html`：浏览器直接读库，只读。
- 只放机械统计：活项目、停滞项目、deadline、进行中的旅行计划、Inbox / Unclear 积压、策略证据等级、侧写更新日期、格式体检。
- 不写判断与建议。

### 6.10 strategy 证据等级

- **等级行**：frontmatter 下面第一行，固定写法：
  `> 🟡 部分验证 · 验证 3 次（支持 2 / 反例 1）· 更新 2026-10-14`
  一行只写这些，说明另起一段写在下面。
- **什么算一次验证**：一条**第一手现场**，即用户亲历并记录下来的一件事，出处是 B-Emotions、B-Insights、B-Dialogues（复盘类，只算其中用户本人的经历）或 A 层进展日志。AI 的分析、别人的经验、书和播客、理论**不算**，写进 **来源** / **理论依据**。
  - 同一件事的多条记录（如同一天的 emotion + insight）合算 **1 次**。
  - 建策略时用的原料也算，不区分建策略之前还是之后。
- **支持还是反例**：
  - **支持**：识别信号里的模式出现了、机制解释得通；或照破解步骤做了，结果符合预期。
  - **反例**：模式出现了但机制解释不通；或照步骤做了，没用或适得其反。
- **四档**（先看反例，再看支持）：
  - 🔴 **存疑**：反例 ≥ 1 且 反例 ≥ 支持。
  - ⚪ **待验证**：支持 0 次。
  - 🟡 **部分验证**：支持 1–2 次。
  - 🟢 **已验证**：支持 ≥ 3 次。
- **多步策略**：证据按步骤分栏（`**证据**（第 1 步）：`）。只要有一步还是 0 次，整条最高到 🟡 部分验证；等级行里注明缺哪一步。
- **证据栏写法**：`## 关联链接` 里，支持放 **证据** 栏，反例放 **反例** 栏，每条一行 `- [[原记录]]（YYYY-MM-DD）—— 一句话说明`。「仍缺什么」的 TODO 和「证据集中度（供审计）」说明照旧保留，不计次数。
- **谁来改**：AI 在巡检（第八节）或用户要求时，把新原料归进证据栏后重算等级、改等级行和 `updated`。用户说某条策略「不对」「没用」时，按反例处理（先按 3.1 把这句话入库）。
- **存疑不删**：存疑的策略照旧保留，由用户决定改写还是归档。

### 6.11 profile（用户侧写）

- **一份文件**：库根目录 `C-侧写.md`，type `profile`。作用是让任何 AI 一打开就知道用户是什么样的人、在忙什么、要注意什么。
- **结构**：
  - `## 画像`：是什么样的人（目标、长处短板、常见模式、和他打交道要注意的）。**每月 1 日巡检时整节重写**（见 8.2），用户要求时也可重写。不超过 30 行；第一行写 `更新 YYYY-MM-DD`。
  - `## 近况`：在做什么（活项目、最近的 deadline）、最近状态、这几天要注意的。**每天由定时任务（如 08:00 的早间简报）整节重写**，只改这一节。不超过 15 行；第一行写 `更新 YYYY-MM-DD`。
  - `## 关联链接`
- **每条都带出处和日期**：事实链接原记录；用户原话放「」；推测标「（AI 判断）」（见 4.1）。
- **情绪内容**：只写一行概括 + 链接，不抄心理活动原文。
- **不当证据**：其他 C 文件不得把 `C-侧写.md` 当证据引用；要引用就引用它链接的原记录。
- **不写**：只服务当前工作的安排（如近期优先级排序）、证件号等隐私原文（同 6.8）。
- **为什么允许写「这几天要注意」**：这一节每天整份重写，不会过期，所以不违反铁律 6；但只写依据记录能说出来的提醒，不替用户定计划。
- **留痕**：近况每天覆盖，不留历史；画像每月重写时，在当月巡检日志里写一行「画像改了哪几条」。

## 七、字段取值表

| 字段 | 用于 | 写法 | 取值 |
|---|---|---|---|
| `type` | 全部 | 单值 | project · holiday · emotion · insight · topic · dialogue · readme · changelog · info · strategy · situation · knowledge · memoir · unclear · profile |
| `status` | project、holiday | 单值 | planned · active · done |
| `created` | 全部 | `YYYY-MM-DD` | 建档日期 |
| `updated` | 除 emotion、insight、unclear 外全部 | `YYYY-MM-DD` | 最近一次实质修改的日期 |
| `start` | holiday | `YYYY-MM-DD` | 出发日期，未定则留空 |
| `period` | memoir | `YYYY-QN` | 如 `2026-Q3` |
| `goal` | project | 单值 wikilink：`"[[学业]]"` | [[学业]] · [[职业发展]] · [[身体健康]] · [[生活与体验]] · [[终身学习]] |
| `situation` | emotion、insight、strategy | wikilink 数组：`["[[决策]]", "[[压力]]"]` | 启动-执行 · 压力 · 决策 · 人际关系 · 自我价值与意义感 · 规划 |
| `emotiontype` | emotion | wikilink 数组：`["[[fear]]", "[[sadness]]"]` | anger · disgust · fear · joy · peace · poignant · sadness · shame · surprise |
| `field` | topic（数组，只放一个值）、knowledge（数组，可放多个） | wikilink 数组：`["[[AI]]"]` / `["[[AI]]", "[[金融]]"]` | AI · 身心 · 金融 · 科研方法 · 阅读 · 工具 |

**取值规则**：

## 八、巡检与定期蒸馏

### 8.1 触发
- **定期**：每月 1 日由定时任务发起一次；用户说「巡检 / 蒸馏一下」时随时发起。
- **增量**：只处理上次巡检之后新增或更新的 B 层文件；上次日期以 [[个人数据库]] 进展日志里最近一条「巡检」记录为准。没有记录时做全量。

### 8.2 步骤
1. **找新原料**：列出 created / updated 晚于上次巡检日期的 B-Emotions、B-Insights、B-Dialogues、B-Topics、B-Tools 文件。
2. **找未被引用的原料**：在新原料里，筛出还没被任何 C 层文件的 **证据** / **反例** 栏引用的文件。
3. **归入已有 C 文件**：能归到已有 strategy / situation / knowledge 的，追加进它的 **证据** 栏并更新结论，改 updated。改动过证据栏的 strategy，按 6.10 重算等级行。
4. **提议新建**：同一 situation 下有 3 条以上未被引用、且指向同一模式的原料时，提议新建 strategy；新的情境类别、knowledge 体系一律先提议，用户同意后再建。
5. **季度回忆录**：巡检日期在 1、4、7、10 月时，按 6.5 生成上一季的 memoir。
6. **重写画像**：按 6.11 重写 `C-侧写.md` 的 `## 画像`，原料是上月新增的 B 层记录、A 层进展日志、已有画像和各 strategy 的等级。
7. **顺带格式巡检**：只查不改原文。查 frontmatter 取值、目录与 type、status=done 未归档、断链（只看新文件）。

### 8.3 产出
- 在 [[个人数据库]] 进展日志追加一条 `### YYYY-MM-DD · 巡检`，写清：处理了哪些原料、改了哪些 C 文件、提议了什么、画像改了哪几条、哪些 strategy 等级变了、发现的格式问题。只列事实。
- 需要用户决策的项放进 `0-Unclear/`（按 6.7 模板）或在对话里列出，不自行决定。
- 没有新原料时，日志只记一行「无新原料」。
